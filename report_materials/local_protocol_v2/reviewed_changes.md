# Проверенный разбор изменений, без исправления прогнозов

Один exploratory-прогон на тех же 18 ID. Код не изменялся после freeze; ниже анализ уже сохранённых outputs/traces. Примеры иллюстративны, не отдельная статистическая выборка.

## Координация исправлена, но E стал опаснее

В v1 terminal coordination stops: C=5, D=18, E=15; ещё один review C был вызван невалидным JSON. В v2 нет ни review, ни ошибок JSON/ссылок. **Схема всё ещё допускает substantive manual_review** — его сохранение проверено тестами, но реальная Qwen во всех 54 итоговых случаях выбрала автоматический класс. Нулевой review нельзя трактовать как принудительное исключение abstention из schema или как доказательство достаточности входов.

У E attack allow вырос 1/12→5/12. Парное сравнение показывает **5 новых** опасных допусков после прежнего coordination review и **1 устранённый** прежний допуск; это не просто четыре одинаковых ошибки. Все пять новых относятся к сценарным injection_attack. Полный список: new_dangerous_allows.jsonl.

### 71c6d2f1c67a0faa2fbca11f157b6636 — слабая наблюдаемость и игнорирование ролей

v1 E: review из-за повторного запроса проверки. v2 E: bona_fide/allow, ссылка только v0. Визуально PAD live, live_score≈0.999984; канал synthetic valid/match, клиент заявляет virtual_camera. Это stealth-сценарий: виртуальная камера сама не доказывает внедрение, а доступные поля близки к доброкачественным. Ground truth здесь сценарный; по таким данным нельзя обещать надёжное восстановление скрытого способа доставки.

При этом reasoning неверен и сверх этой проблемы наблюдаемости. Context-аналитик утверждает capture binding mismatch и device change, хотя в c1 стоят match и device_change=false; называет историю success признаком presentation_attack. Verifier копирует визуальное обоснование bona_fide, не записывает противоречие с выводом context и не опирается на весь пул свидетельств. Корректные evidence_id не гарантируют истинности пересказа или проверки полноты.

### 908ed4ffed802aea883bf9eca2ff4fe1 — проигнорированная аномалия канала

v1 E: coordination review. v2 E: bona_fide/allow со ссылкой только v0. c1 содержит **invalid attestation**, unknown binding, device_change=true и timestamp_gap_ms=604. Context отмечает аномалию, но ошибочно относит её к presentation_attack. Verifier вновь выбирает визуальный live и утверждает отсутствие противоречий/пропусков. Это не подтверждение подлинности канала: PAD appearance не проверяет доставку. Даже если нельзя доказать injection по synthetic полям, confident allow здесь не обоснован как безопасный вывод.

Эти два случая различаются: первый намеренно плохо различим по доступным данным, во втором видимая канальная аномалия не попала в итоговое обоснование. Нельзя объяснять все новые ошибки одной причиной и нельзя считать telemetry проверкой реальных внедрений.

## C/D: опасных допусков не прибавилось, но hard reject вырос

C: allow атак 7/12→4/12, новых индивидуальных unsafe allow нет, устранено 3. Верных автоматических классов 4→8. Однако benign hard reject вырос **1/6→3/6**, escalate снизился 2/6→0/6. Неизменные 3/6 для суммы reject+escalate скрыли бы важную смену последствий.

D: attack allow остался 0/12, верных автоматических классов 0→9, но benign reject стал **3/6** вместо 0/6; прежние 6/6 escalate исчезли. Ни один из шести injection-сценариев не классифицирован как injection_attack: они отвергнуты как presentation_attack. Нулевой allow не равен правильной атрибуции способа атаки.

## Инструменты и вычисления

В v2 C ни разу не запросил проверку (18 вызовов), D выполнил одну context-проверку на каждый инцидент (54 вызова), E ни разу не воспользовался правом проверки verifier (54 вызова). В E аналитики сформировали 36 реальных ответов с финальной schema none, в D после checks — 18 таких ответов. Реальный post-check путь E в оценке не активировался; его переход проверен unit/debug-тестами, а общая финальная schema проверена на реальных D/E-ответах. Эти различия usage — часть результата, не скрытая оптимизация.

Всего v2: 126 вызовов, 107036 входных / 17957 выходных токенов, сумма времени триажа 1238.666 с. v1 на тех же ID: 152 вызова, 125599 / 22467 токенов, 1347.814 с для C/D/E (A/B занимали ещё около 0.002 с). Денежная стоимость API обеих серий — 0; сравнение latency ограничено порядком/прогревом, временем запуска и CPU-фоном. Это не доказательство ускорения от одной только schema.

## Вывод для защиты

Система стала корректнее завершать протокол, но корректность завершения **не обеспечивает безопасность автоматического решения**. Для C/D на этой повторной малой выборке число опасных допусков не выросло, хотя увеличились ложные hard reject. Для E заявленная цель без роста опасных допусков не достигнута. Улучшившийся macro-F1 не отменяет этого результата. Сравнение joint schema+policy, после просмотра v1; статистическая значимость и независимое подтверждение не заявляются.
