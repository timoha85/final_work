# Краткая инструкция для защиты

1. **Что было сломано.** В v1 разрешённый tool request оставался доступным даже после исчерпания единственной проверки. Повторные/конкурирующие запросы приводили к системному review; у D 18/18 review и E 15/18, а не успешная классификация всех атак.

2. **Что изменили.** State-dependent действия: финальный JSON допускает только request_check=none в constrained decoder и валидаторе. D программно отдаёт одну проверку context раньше visual и не считает невыполненный второй запрос ошибкой. В E инструменты принадлежат только verifier. Содержательные классы, данные, модель и merge не меняли.

3. **Как проверили.** До evaluation — тесты конкурентных запросов, запрета request_check в final, содержательного review, невалидного JSON, отказа инструмента, лимитов и partial checkpoint; два реальных debug-инцидента. Затем SHA-256 freeze и один прогон на прежних 18 ID.

4. **Что измерили.** Macro-F1, опасные allow/12, benign reject и escalate отдельно/6, review/18, coverage, верные auto, причины отказов, фактические вызовы/токены/секунды. Парные переходы показывают, куда исчезли отказы: в правильные решения или ошибочные допуски.

5. **Что получилось.** Рост числа опасных допусков наблюдается в методах E. Гипотеза уменьшения координационных отказов БЕЗ ухудшения опасных допусков для этих методов не поддержана.

6. **Чего не утверждаем.** Это exploratory анализ тех же зависимых данных после просмотра ошибок, не новое независимое подтверждение. Совместный эффект схемы и координации; статистической значимости и работоспособности на реальном внедрении не заявляем.

Для чисел показать comparison.md и таблицу safety_changes.csv; для одного конкретного опасного перехода — new_dangerous_allows.jsonl и соответствующий trace. Не защищать архитектуру обещаниями: ухудшение является допустимым измеренным результатом.
