# Фактическая архитектура и методы

Дополнение: активная LLM-ветвь переведена на бесплатный loopback llama.cpp с Qwen2.5-1.5B-Instruct Q4_K_M. Платные/удалённые вызовы блокируются. Ключ и LLM_BUDGET_USD не требуются; API cost=0. Старые упоминания бюджета внешнего API ниже описывают исходный план; фактическая локальная конфигурация и одинаковый для C/D/E JSON Schema decoder описаны в local_backend.md и local_protocol_addendum.md. Prompts, правила и merge сохранены.

## Границы компонентов
`triage.pad.PAD` — инструмент локального нейросетевого вычисления, не агент. `build_input` — программный фильтр, допускающий в LLM только incident_id и список типизированных Evidence. `Orchestrator` — конечный программный конвейер, не LLM-агент. Агентами являются LLM-вызовы с отдельными задачами visual, context, verifier и single, с JSON-схемой, анализом предоставленных свидетельств и возможностью адресно запросить ограниченный инструмент. Тестовый ScriptedLLM используется исключительно в unit-тестах и никогда в экспериментальном runner.

Роли: visual получает только визуальное свидетельство v0; context — c0/c1/h0; verifier получает весь исходный набор и предварительные выводы. Single получает весь исходный набор. Оркестратор ограничивает повторную проверку и проверяет JSON/ссылки/согласованность рекомендации. Итоговый вывод включает predicted_class, recommendation, evidence_ids, contradictions, missing_data, rationale. Ground truth не загружается агентным модулем; runner читает её только для состава выборки и метрик. В строгом production-разделении процесс метрик следовало бы изолировать физически; здесь проверяется отсутствие полей разметки в сериализованном агентном входе.

## PAD
Готовый MiniFASNetV2 в ONNX, опубликованный yakhyo/face-anti-spoofing на основе minivision-ai/Silent-Face-Anti-Spoofing. Веса не обучаются и не дообучаются. CPUExecutionProvider, 2 потока ONNX, детектор Caffe из официального репозитория. Resize для детектора до площади около 192² с сохранением пропорций; BGR, вычитание (104,117,123). Принимается ровно одно лицо с confidence ≥0.6; иначе ошибка инструмента.

Для PAD используется bbox, расширенный в 2.7 раза с переносом обрезки внутрь границ изображения по официальному generate_patches.py. Resize 80×80, BGR float32, NCHW, диапазон 0–255, без нормализации /255. Это сохраняет официальный граничный crop, который отличается от упрощённого clipping в ONNX-примере yakhyo. Softmax применяется к трём логитам. Индекс 1 = real/live проверен по официальному test.py и ONNX inference reference. Индексы 0/2 объединяются как spoof, их конкретные разновидности не интерпретируются. Softmax не является откалиброванной вероятностью атаки.

Из видео извлекаются кадры на 20/50/80% длины, из фото один кадр. На источник усредняются softmax-векторы и берётся argmax; при ошибке хотя бы одного кадра агрегат помечается error и не используется для автоматического визуального заключения. В кэше сохраняются также детекторный балл, яркость и дисперсия Лапласиана по кадрам; текущие агенты получают только агрегат PAD, число валидных кадров и разброс live score. Выбор визуальных признаков намеренно компактен и одинаков для методов B–E. Для A доступна только визуальная часть.

Хеши источника и весов сохраняются в visual_cache.json, хеши файлов кода/протокола/данных — в конфигурации запуска. Детектор и загрузка модели происходят вне таймера обработки источников. feature_seconds включает PAD-обработку и сохранение извлечённых кадров, но не загрузку модели и не сетевую загрузку исходников. Поэтому не является чистым benchmark нейросети. triage_seconds измеряется отдельно. Холодный старт и повторный прогрев не сравниваются.

## Методы A–E
A: бинарный PAD, live→allow, spoof→reject; error→manual_review/escalate. В трёхклассовую задачу A не включается.

B: если synthetic server observation содержит одновременно invalid attestation и mismatch capture_binding → injection_attack. Если PAD недоступен → review. Если PAD spoof и binding mismatch → review (неясен способ атаки), иначе spoof → presentation_attack как эвристическая атрибуция. Если PAD live, но нет одновременно valid attestation и matching binding → review; иначе bona_fide. Виртуальная камера сама по себе не является основанием отклонения. Поля истории и клиентского текста доступны правилам, но в итоговой формуле решения не используются: это ограничение baseline, а не скрытый извлекатель сигналов.

C: одна LLM, до одного запроса проверки и одного финального ответа (1–2 вызова). D: 2 специализированных аналитика и программное объединение, максимум одна дополнительная проверка у одного аналитика (2–3 вызова). Если один аналитик abstains → review; разные типы атаки → review; совпадение → общий класс; attack против bona_fide → attack с записью противоречия. E: два аналитика и LLM-верификатор (3–4 вызова), перепроверку запрашивает только verifier. Запросы аналитиков в E сохраняются, но не выполняются; verifier решает, нужна ли проверка. Различия числа вызовов являются частью сравнения и должны учитываться в расходах. D и E выполняют свои аналитические вызовы раздельно, общих кэшированных LLM-ответов нет.

Все C/D/E: одна LLM_MODEL, temperature=0, до 600 выходных токенов на вызов и 4 вызовов на метод, таймаут 40 с/вызов, максимум одна перепроверка. Общий верхний предел 2400 выходных токенов сопоставим, фактические расходы различаются. Расход входных токенов отдельно. Ограничение всей серии `--max-api-calls` предохраняет от неограниченного числа запросов. Денежный лимит сам по себе не вычисляется без проверенной цены: LLM_BUDGET_USD фиксирует разрешение, а жёсткий машинный предел задаётся числом вызовов. До запуска следует выбрать его по цене провайдера. Точный абсолютный сквозной таймаут ОС не гарантирован: urllib использует сетевой таймаут, а не отдельный отменяемый процесс.

Разрешённые инструменты consistency и visual_summary повторно агрегируют уже известные поля. t0 имеет provenance=derived и derived_from; это не новое свидетельство. Повторный request_check после единственной проверки → manual_review. Невалидный JSON, несогласованная рекомендация, неизвестный evidence_id, ошибка API и таймаут → manual_review с записью ошибки. Никаких производственных сервисов/блокировок нет. Prompts и JSON Schema включены в каждый trace.request без ключа API.

## Оценка
Реализация метрик находится в triage/metrics.py, определения и знаменатели — в зафиксированном протоколе. Abstention считается FN истинного класса в recall/F1 и остаётся отдельным столбцом матрицы. Precision без предсказаний и F1 без положительных случаев принимаются равными нулю для macro-F1; в CSV нулевой знаменатель отдельной доли оставлен пустым. Ошибки не исключаются. Selective accuracy всегда сопровождается coverage. Для A бинарные F1 и матрица используют исходную визуальную метку live/spoof; общие показатели attack_allow и benign reject/escalate используют сценарный ground truth. Поэтому PAD может быть визуально прав и одновременно пропускать сценарное внедрение. Selective accuracy A относится к визуальной задаче, B–E — к сценарной; напрямую их не сравнивать.
